# Audio investigation — 2026-10-31

Upstream is `orrpunk-art/virtual-mpc-sample`, pinned at `78d28cea1efe7e16b8a15a86465a64f432945a41`. A live `git ls-remote` check found the same main revision. The public issue list had one SD/autoboot setup issue, no audio fix. Upstream `docs/PANEL.md` explicitly distinguishes measured bridge signal levels from audible Mac playback, which it did not verify.

Sav heard only clicks/pops from the WebKit player, while an `afplay` Mac test chime was audible on Universal Audio. CoreAudio initially reported 48 kHz and later confirmed Sav's intended 44.1 kHz setting; preferred output channels are 1–2. No global device setting was changed by this investigation.

Measured during emulator playback:

- Guest stereo peaks reached about 0.10, phones about 0.26. Host drops were zero and the guest underrun counter did not change during the first short test.
- WebKit's context and worklet both reported 44100 Hz, running state, and input/output peaks around 0.10. Thus a 48 kHz context mismatch does not explain the live failure.
- PCM traffic reached the worker at about 176400 bytes/s. Worker delivery gaps reached 60–69 ms, and the worklet's underrun counter increased. These explain some clicks, but do not establish the cause of the near-silence Sav heard.
- Separately, a synthetic steady PCM test exposed a sample-rate conversion bug in the copied worklet at 48000 Hz: 17 underruns in five seconds. Scaling its read ratio by 44100/outputRate preserves the sine amplitude and eliminates those simulated underruns at both 44100 and 48000 Hz.

The app now offers the same native display and direct-touch integration while AVAudioEngine/AVAudioPlayerNode plays the unchanged upstream S16_LE stereo 44100 Hz WebSocket stream. The page receives `audio=native` and does not open a second PCM client. Native playback prebuffers 2048 source frames (about 46 ms at 44.1 kHz) and bounds queued latency; logs record hardware format, received frames, queued frames, peaks and underruns. Reconnect and Stop close/release the socket and engine. Chrome fallback retains the browser player.

Automated checks: native PCM signed/stereo/little-endian conversion and malformed-frame handling; synthetic five-second sine playback at both output rates; existing direct-touch packet/coordinate and page hold/drag/release checks. These are software checks. Audible native playback requires Sav's test and is not established by nonzero meters.

Sav confirmed the native audio path is audible on the Apollo, with some clicks and pops remaining. A trial with a 4096-frame adaptive host buffer still produced clicks and Sav reported too much delay, so 2048 frames was restored. With the larger buffer, the host queue remained fed while the guest ALSA xrun counter increased from 160 to 190 in ten seconds. Guest-side dropouts are established; host scheduling and screen-refresh workload are possible causes, not yet proven. A CPU snapshot showed QEMU about 38% of one core, which does not reveal brief scheduler stalls. No change was made to the guest firmware, driver, or DisplayLink.

The 4096-frame host-buffer trial was audible but Sav reported too much delay and continuing clicks. The guest `xrun_counter` rose from 160 to 190 over 10 seconds with the larger host buffer; the host queue stayed fed in that interval. The upstream `tools/wakelat.c` helper was compiled separately using the already-built `mpclab-tools` image, copied to guest `/tmp`, and removed after a 10-second run. It recorded 8626 wakeups, 24 over 6 ms late, worst 17.8 ms; the guest playback xrun counter increased from 180 to 212 in that run. The diagnostic itself runs a 1 ms realtime thread and can perturb scheduling, so this is evidence of latency under diagnostic load, not proof that every click has the same cause. The prior 30-xrun measurement did not run this helper. Guest scheduling is a likely contributor; no tested fix for those guest underruns has yet been established.

## Follow-up trials

A guest minimum buffer of 2048 frames was accepted but the Sample continued keeping only about 360 playback frames queued; one ten-second sample recorded 17 xruns. It did not provide the intended extra headroom. The original launcher setting was restored. A temporary per-QEMU IOKit power assertion and a high latency/throughput tier request did not eliminate xruns. Temporarily disabling extra QMP screen bursts also left 30 guest xruns in ten seconds, so normal screen behavior was restored and no performance endpoint was retained in source.

A separately built lab-kernel variant added a `min_period` constraint and was booted with 512-frame periods. The app reported the new period but crashed with SIGSEGV on startup. The original lab kernel was restored from a preserved local copy, and the running guest was verified back at 128-frame periods / 1024-frame buffer. No Akai firmware, protected host driver, or vendor Git source was modified. The failed variant was not retained as a production feature; build artifacts and the rollback image are ignored under `out/`.

The restored four-vCPU configuration recorded 21 guest xruns in a ten-second sample, while the host native queue had zero underruns in that interval. The single-vCPU comparison recorded 9 guest xruns in its first measured ten-second interval, but continued accumulating xruns and is not an established improvement. At handoff the guest playback counter was 837, and recent native logs showed 107 queue underruns. These are cumulative counters over different intervals, not directly comparable rates. The native underrun counter is based on scheduled-buffer completion bookkeeping, not a direct CoreAudio hardware xrun measurement. Both sides need further investigation; neither a CPU-capacity diagnosis nor a fix has been established. The single-vCPU launcher experiment remains active and uncommitted; see `CLAUDE_AUDIO_HANDOFF.md` for rollback and current state.

## Idle-poll trial (2026-10-31, Claude)

One-vCPU baseline right before this trial: 34 guest playback xruns in 10 s (268 -> 302), and `hw_ptr` kept resetting, so the Sample's watchdog was restarting the stream. Theory: under HVF an idle guest vCPU executes WFI and QEMU sleeps the host thread until the next guest timer; macOS wakes it late (wakelat saw up to 17.8 ms against a ~7 ms playback queue). The lab kernel has `nohlt`, which makes idle vCPUs poll instead, so timer ticks no longer need a host wakeup. `lab-ext/qemu-tune` adds it and sets the vCPU count (trial default: 2 vCPUs, costing about two busy host cores). `scripts/xrun-rate.sh` measures the rate read-only. Stock VM: `TS_QEMU_SMP=4 TS_GUEST_IDLE_POLL=0`. First result, 2 vCPUs with idle polling: 2, 6, 0 and 3 xruns in four 10 s samples (about 3 per 10 s, down from 21 on stock 4 vCPUs and 34 on 1 vCPU). QEMU used about 197% CPU. Fewer, not zero; listening result pending.

Listening result for the 2-vCPU idle-poll trial: Sav reported it sounded worse. The native host counter rose while QEMU held two busy cores, so the launcher default went back to the stock VM.

## Real-time vCPU trial (2026-10-31, Claude)

Pro Tools and SoundFlow were not running; WindowServer (~35%) and DisplayLink (~29%) were the busiest host processes beside QEMU (~32%). `lab-ext/qemu-tune/rtboost.c` is injected into QEMU with `DYLD_INSERT_LIBRARIES` (Homebrew QEMU is ad-hoc signed, no hardened runtime) and gives the `CPU n/HVF` threads the macOS time-constraint policy (1 ms period, 0.5 ms budget, preemptible), so they are not woken late behind WindowServer/DisplayLink. Tested on a dummy process: the named thread ran at priority 97R, the others stayed at 31. `TS_QEMU_RT=0` turns it off. Result: after Sav restarted at 06:43 with the default launcher, `ps -M` showed the 4 vCPU threads at 97R, and guest playback xruns were 0 in four 10 s windows (2 total since boot) with the Touch connected and audio playing; host native underruns 0. Before: 11-52 per 10 s. Sav had noticed that disconnecting the Touch helped; the Touch screen keeps WindowServer and DisplayLink busy, which the vCPUs no longer lose to. New issue: with no xruns, the native host queue grows by about 6 frames/s (4096 -> 5632 in 4 min), so the guest clock runs about 140 ppm fast against the Apollo and latency creeps up until the 16384-frame bound drops audio. Fixed in NativeAudio.swift (70c1eb0): outside target 2048 +/- 1024 frames each ~256-frame packet is linearly resampled by one frame until the queue is back within 512. After an app-only restart: queue held 2816-3328 frames (~65-75 ms) for a minute, underruns only during startup (4), guest xruns 0 in 30 s. Listening result pending.

## Panel A/B (2026-10-31, Claude)

Upstream (78d28ce, still latest) reports 6-11 app stream restarts per minute on its own Mac; we measure 11-21 guest playback xruns per 10 s on stock 4 vCPUs while Sav plays a sequence, with 0 host native underruns in the same windows. Freezing the panel server (SIGSTOP, 10 s) during a sequence gave 12 -> 6 -> 11. That pause also stops the panel UART (pad lights / LEDs) and bursts, not only VNC. A 15 fps cap on VNC update requests (`TS_SCREEN_FPS`, panel-ext) then measured 14, 23, 11: no gain, so it is off by default. Single 10 s windows vary widely; use several before concluding.
